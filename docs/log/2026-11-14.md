### Found / learned
- **QMK's backlight feature can't breathe four pins on the RP2040.** Its `pwm` driver drives one pin; the `timer`
  driver needs a ChibiOS GPT driver, and the RP port has none (`lib/chibios/os/hal/ports/RP/LLD/`: DMA, GPIO, I2C,
  RTC, SPI, TIMER, UART, WDG; `lib/chibios-contrib/os/hal/ports/RP/LLD/`: ADC, I2C, PWM, USBD); the `software`
  driver doesn't support breathing (`docs/features/backlight.md`). So the LEDs use own PWM code.
- **QMK's generic RP2040 board puts I2C on `I2CD1`, GP2/GP3** (`docs/platformdev_rp2040.md`), which are K1/K2 on
  this board. `config.h` must override `I2C_DRIVER`, `I2C1_SDA_PIN` and `I2C1_SCL_PIN`. QMK keeps the `I2C1_` pin
  names whichever controller is used (same as `keyboards/beekeeb/3w6hs/config.h`).
- **QMK turns on the RP2040's internal pull-ups on the I2C pins** (`PAL_RP_PAD_PUE` in `I2C1_SDA_PAL_MODE` /
  `I2C1_SCL_PAL_MODE`, `platforms/chibios/chibios_config.h`). The Rev A OLED test therefore ran with the module's
  pull-ups plus the internal ones; it does not show the module's alone would do.
- `pwmcnt_t` is `uint16_t` on the RP port (`hal_pwm_lld.h`), so `keymap.c` computes the PWM width in 32 bits
  instead of using `PWM_FRACTION_TO_WIDTH`.
- **Unconfirmed:** ChibiOS writes the configured period (1024) straight into the slice's `TOP` register. If the
  RP2040 counts 0 to `TOP` inclusive, a cycle is 1,025 ticks and "full" is 99.9 %. Not checked in the RP2040
  datasheet's PWM chapter (assumption).
- QMK resets the OLED cursor to (0, 0) before each `oled_task_user` call (`drivers/oled/oled_driver.c`), so the
  hook redraws the whole screen every time.
